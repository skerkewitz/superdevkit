# Status review, 2026-11-18

A look at where dampf stands after two days of work (160 commits, about 23,000 lines of Java in
`src/main` and 4,200 in `src/test`). It answers whether dampf is usable, what is wrong with it
in the small and in the large, and what could still go badly. The second half collects every
open question and every todo from the working documents in one list, plus the ones this review
found, so they can be moved into [roadmap.md](../roadmap.md).

This file is a snapshot. Its figures are from the day it was written; the current ones are in
[optimizations.md](../optimizations.md#where-things-stand), the milestone state in
[roadmap.md](../roadmap.md). Archived the same day: its list moved into the milestones M5 to M10
of the roadmap, and its risks into the roadmap's risks.

## Where dampf is

M0 to M2 are done, M3 is in progress (its goal, faster than Calypsi, is reached), M6 is done
ahead of plan, and M5 has not started. `./gradlew build` passes (2 minutes 7 seconds on the
day of this review).

All of Blubber Blasen compiles. The benchmark's 3,610 ticks and the replay's checksums match the
PC, and the playable ROM runs in Mesen with no byte lost outside the vertical blank. The game
compiles in 11 seconds.

| What | 2026-11-18 |
| --- | --- |
| Play, frames per tick | 0.79 average, worst tick 1.42 (goal: 0.6) |
| Play with the CPU partner | 1.36 average, worst tick 3.03 |
| Against Calypsi | 2.14 times as fast, on the 102 ticks where both play the same scene |
| Against the naive code generator | 5.5 times as fast |
| Against hand-written `level_solid_px` | 1.14 times the cycles |
| Playable ROM in Mesen | 1.57 frames per tick, waiting for the vertical blank included |

## Is dampf usable?

For Blubber Blasen, yes. It is correct on everything the tests check, faster than the other
compilers, and the ROM can be played. It is not yet within the frame budget, and the platform
layer has no sound and no save RAM.

For anyone else, not yet. dampf is not public, it needs gcc, and its subset and platform layer
are shaped by one game. A new user would also run into the usability gaps below within the
first hour.

## Usability flaws and smaller gaps

1. **Only the first error is reported.** A file with three violations of the subset needs three
   runs; the compiler stops at the first error.
2. **No library.** There is no `<string.h>`: `#include <string.h>` fails with "No such file or
   directory", so there is no `memset` or `memcpy`. There are no intrinsics for the hardware
   multiplier, the divider or DMA either; multiplication and division by variables are software
   routines in the runtime.
3. **gcc for preprocessing.** On Windows a user installs MinGW or MSYS only for `gcc -E`.
4. **Debugging in Mesen shows little beyond the source.** Mesen shows the C source and the names
   of globals. It does not show locals, C types or struct fields, and the code from MIR writes no
   processor state line in the assembly.
5. **Gaps in the timing analysis.** 37 of the game's functions have no worst case. The figures
   are CPU cycles, not master cycles, and a budget error does not say which path is the costly
   one.
6. **Memory.** Enum objects and pointers take 4 bytes each, bank `$7F` is unused, and compiling
   the game takes 1.8 GB of the JVM's memory.
7. **Known slow code.** A constant shift by more than 8 is a loop (a 32-bit shift by 16 costs
   about 600 cycles). `switch` has no jump table, copies use no `MVN`, and the block layout by a
   profile is opt-in.
8. **Open subset decisions:** the signedness of plain `char`, the size of enum objects, `goto`
   ([subset.md](../subset.md), decisions 1 to 4).
9. **`--replace` works only with the naive code generator**, so a hand-written function cannot
   be linked into an optimized build.

## Flaws in the architecture and the design

1. **C cannot run in an interrupt.** Frames have fixed places, so C code called from an NMI or
   IRQ would overwrite the frames of the code it interrupted. Nearly every SNES game has an NMI
   handler, and raster effects need an IRQ handler. The platform layer works around it by waiting
   for the vertical blank in the main loop. [optimizations.md](../optimizations.md#knowing-the-machine)
   says dampf "sees what the NMI and IRQ handlers touch", but nothing of that is built or
   designed in detail. The whole call graph is known, so the functions reachable from an
   interrupt can get a frame area of their own. That is a design decision that should come
   before M5, since it affects the memory map and the subset.
2. **Register allocation is a collection of special cases.** Loop counters in X, indexes in Y,
   values handed on in A, `PointerRemat`, `ByteStretches` and others each cover one pattern, and
   no common model decides what lives in A, X and Y. Every new pattern interacts with the
   others, and the open miscompilation below shows that these interactions are already hard to
   follow.
3. **The processor state is not followed across blocks.** `REP`/`SEP` are not placed across
   blocks, and X and Y always run at 16 bits. Roadmap rows 3 and 5 (8-bit stretches, 8-bit index
   registers) wait for this.
4. **HIR is missing, and with it the split of struct arrays** (catalogue D, `DAMPF_SPLIT`), one
   of the larger remaining gains: the bubble loops are 30 % of play. It needs both a subset
   decision and the IR level to put it in.
5. **Pointers are 4 bytes.** 16-bit pointers into RAM are not built; only pointers into one
   known object are compressed. The struct layout differs from gcc's (no padding), which is why
   `sizeof` must be restricted.
6. **No function pointers, not even in constant tables.** Tables of handlers for state machines
   are common in game code. The subset allows them by design, but they are not built.
7. **The split between the 65816 core and the SNES target exists mostly on paper.** The code
   generators contain SNES facts themselves: DBR `$7E`, the frame addresses, long addresses for
   I/O registers ([architecture.md](../architecture.md#core-and-target)).
8. **Tuned on one game.** The inlining limit, the block order and the idioms the optimizer looks
   for come from Blubber Blasen. The optimizations of 2026-11-18 made the game's play 13 %
   faster and the execution tests 0.9 %.

## Risks and uncertainties

1. **A known miscompilation is still unfound.** With functions of up to 80 instructions inlined,
   the benchmark differs from the PC from tick 32 on. The MIR is right, so the fault is in the
   older part of the code generator (selection, `FrameLayout`, the masks). The limit of 60 only
   avoids the function that shows it; a change in the game can produce such a function at any
   time. This is the most urgent item.
2. **The tests are thin for an optimizer this size.** There are 29 execution tests and 50 random
   programs per build. The random programs spend their cycles in the division routines and
   barely reach the optimizer's patterns. In practice the optimizer is tested by one game and
   one replay recording.
3. **The budget may be out of reach for the compiler alone.** The worst tick with the CPU
   partner takes 3 frames. The checkpoint after M2 concluded that the game has to do less work,
   so the result depends on work outside dampf ([game-findings.md](../game-findings.md), finding 1).
4. **Never run on a real console.** All checks run in dampf's emulator and in Mesen. FastROM,
   the DMA margin (`SETUP_LINES`, not measured again) and the timing at the edges have not run on
   hardware or a flash cartridge.
5. **The comparison with Calypsi is weak.** Calypsi drifts from the PC from tick 596 on, for
   reasons not known, so the factor of 2.14 rests on 102 ticks.
6. **Fast growth, little human knowledge of the code.** 23,000 lines in two days, mostly
   written by AI agents. Finding a bug like the miscompilation above depends on someone knowing
   how the code generator works, and today most of that knowledge is in the documents.
7. **Scope creep.** The book, its generator and review skills, and M6 came before M5. The
   roadmap names this risk: the compiler becoming the project.
8. **Publishing is a project of its own.** The game's snapshot, its platform layer and
   `reference/` are in the git history, so the history has to be cleaned or the public
   repository starts without it. New benchmarks are needed, and a subset taken from one game may
   be too narrow for other users.
